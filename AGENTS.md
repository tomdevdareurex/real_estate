# AGENTS.md
_Last reconciled: 2025-07-15_

## Overview
- Scraper and parser for **aruodas.lt** (Lithuanian real-estate portal), producing normalized English CSV datasets of apartments and houses.
- Two modes: **online** (live retrieval via `scrape-live`) and **offline** (parse local HTML via `parse-offline`). Both export to `data/processed/`.

## Architecture
- **Entry point**: `src/aruodas_scraper/cli.py` — Typer app exposed as `aruodas` console script; subcommands: `parse-offline`, `scrape-live`, `doctor`, `validate`, `report-unknown-fields`, `show-config`.
- **`__main__.py`** enables `python -m aruodas_scraper`.
- **`run_config.py`** loads `config/scrape.yaml` (the default run configuration); merges with CLI flags (CLI wins).
- **`config.py`** loads a legacy offline-only YAML (`config/default.yaml`); used by `OfflinePipeline`.
- **`cities.py`** loads `config/cities.yaml` — registry of city/category definitions (search URLs, listing-ID prefixes, output filenames).
- **Pipelines**: `pipelines/online.py` (live), `pipelines/all_properties.py` (offline orchestration), `pipelines/offline.py` (snapshot loader), `pipelines/export.py` (atomic CSV/JSON writes).
- **Networking**: `networking/http_client.py` (AruodasHttpClient — caching, retries, redirect following, URL allowlist), `networking/curl_fetcher.py` (CurlCffiFetcher — Chrome TLS fingerprint via curl_cffi), `networking/cache.py` (SHA-256 content-addressed HTML cache in `data/raw/cache/`).
- **Parsers**: `parsers/common.py` (`parse_listing` — shared detail extraction), `parsers/apartment.py`, `parsers/house.py`, `parsers/coordinates.py`, `parsers/engagement.py`, `parsers/structured_data.py` (JSON-LD).
- **Discovery**: `discovery/listing_links.py` extracts listing URLs from search pages; `discovery/pagination.py` tracks pagination state.
- **Normalization**: `normalization/translations.py` loads `config/field_mappings_lt_en.yaml` (Lithuanian→English field/category/feature maps); falls back to a packaged copy in `src/aruodas_scraper/resources/`.
- **Validation**: `validation/records.py` (CSV duplicate check), `validation/quality_report.py` (missingness/duplicate metrics), `validation/coordinates.py` (Lithuania bounding box).
- **Models**: `models.py` — Pydantic v2 frozen models: `ListingRecord`, `DiscoveryRecord`, `FailedUrl`, `ScrapeSummary`, `OnlineScrapeSummary`, `UnknownField`.

## Build & run
- Python ≥ 3.12 required.
- `make install` — installs dev deps + editable package.
- `make test` — runs pytest (unit + integration); `make coverage` enforces ≥ 80 % branch coverage.
- `make lint` — black + isort check; `make format` — auto-format; `make typecheck` — mypy strict; `make security` — bandit.
- `make check` — runs lint, typecheck, security, coverage, and build in sequence.
- CI: `.github/workflows/ci.yml` runs on every push/PR; also installs `ruff==0.12.9` for linting.
- Live scrape workflow: `.github/workflows/scrape-live.yml` — manual dispatch or daily cron (04:17 UTC).
- Run live: `python -m aruodas_scraper scrape-live` (reads `config/scrape.yaml` by default).
- Run offline: `python -m aruodas_scraper parse-offline --input <dir>`.

## Conventions
- All file writes are **atomic** (write to `.tmp`, then `os.replace`).
- CSV export neutralizes spreadsheet formula injection (prefixes `=`, `+`, `-`, `@` with `'`).
- URL fields (`listing_url`, `canonical_url`) are placed last in CSV column order.
- The HTTP client **only allows HTTPS requests to `aruodas.lt` / `www.aruodas.lt`** — anything else raises `RetrievalError`.
- Rate limiting defaults: 10 s minimum + 2–5 s random jitter between every request.
- Offline checkpoints use SHA-256 content digests per file; stored in `data/interim/checkpoints/`.
- Tests are marked `@pytest.mark.unit` or `@pytest.mark.integration`; fixtures live in `tests/fixtures/`.
- `ListingRecord` uses `extra="forbid"` — any unmapped field causes a validation error.
- Field mappings YAML is validated against `ListingRecord.model_fields` at load time.
- The `curl` transport is the production default; `httpx` is kept for tests/offline only (detectable fingerprint).
- Default impersonation profile: `chrome146`. It must agree with the browser that mints `cookie_file` — see the 2026-08-21 note below.

## Auth & security
- **Cookie file** (`cookie_file` in `config/scrape.yaml`): path to a file containing a browser Cookie header; kept outside the repo. Max 16 KiB.
- **CA bundle** (`ca_bundle`): for TLS-intercepting corporate proxies (e.g. Zscaler); also respects `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE` env vars.
- **Proxy**: explicit `proxy` URL (with credentials) for corporate environments.
- `config/scrape.yaml` references `../../aruodas_secrets/cookie.txt` — never committed.
- Max response size: 10 MiB (`MAX_HTML_FILE_BYTES`); max HTML files per offline run: 10 000.
- Symlink HTML inputs are rejected in offline mode.
- Contact details (phone numbers, emails) are redacted from descriptions via `normalization/privacy.py`.

## Gotchas / notes
- Bot protection (PerimeterX) scores TLS fingerprint, HTTP/2 SETTINGS, and header order — not just User-Agent. Only the `curl` transport passes.
- `px-captcha` in a 200 response body is treated as a block (challenge page); the session is cleared before retry.
- Blocked retries use a separate budget: 2 attempts with 30 s backoff (vs. 3 attempts / exponential for transient errors).
- `FetchOptions.transport` defaults to `"httpx"` in code, but the CLI and `config/scrape.yaml` override to `"curl"`.
- Online pipeline merges new records with existing CSV (keyed by `listing_id`); never removes rows absent from the current run.
- Online pipeline abandons the run after 3 consecutive blocks (`_MAX_CONSECUTIVE_BLOCKS`), exporting what was collected so far.
- Offline `--resume` requires the exported CSV to still exist; otherwise raises `CheckpointError`.
- The `_classify` function in `all_properties.py` routes HTML to apartment vs. house parser by inspecting the canonical URL path (`/butai-` + `1-` → apartments, `/namai-` + `2-` → houses).
- `config/scrape.yaml` is the default run config (`DEFAULT_RUN_CONFIG`); `config/default.yaml` is a separate legacy settings file for `load_settings`.
- `DelayPolicy` (networking/rate_limiter.py) is `@dataclass(frozen=True, slots=True)`, so `DelayPolicy.minimum_seconds` read off the *class* is a slot descriptor, NOT 10.0. A module constant `DEFAULT_MINIMUM_DELAY_SECONDS = 10.0` is exported for use as CLI/typer defaults. Never read a default off a slotted dataclass class object.
- `.github/workflows/scrape-live.yml` must pass `--no-config`: the CLI auto-discovers `config/scrape.yaml`, whose `cookie_file` only exists on the local workstation, so CI would abort with "Cookie file was not found".
- `browser_profile._CHROME_MAJOR_VERSION` must stay in step with `curl_fetcher.DEFAULT_IMPERSONATION`; do not bump independently. Both are `146`. This pairing is now machine-checked by `test_the_impersonation_profile_and_the_header_identity_claim_one_version`, so bumping one alone fails the suite. Note the headers only reach the wire on the httpx transport — curl imposes just Accept-Language and takes User-Agent/sec-ch-ua from the profile.
- Key dependencies pinned in `pyproject.toml`: `curl_cffi==0.16.0`, `httpx==0.28.1`, `pydantic==2.11.7`, `selectolax==0.3.29`, `tenacity==9.1.2`, `typer==0.16.0`.
- `config/scrape.yaml` sets `min_delay_seconds: 45.0` and `overwrite: true` — tuned for the per-IP request budget (~11 requests before block).
- (2026-08-18) Aruodas per-IP ceiling is a request COUNT, not a rate: a run paced at min_delay_seconds=45 still collected only 16 detail pages before 403s began, barely more than the ~11 seen at ~13s. Slower pacing therefore buys almost nothing; config/scrape.yaml was lowered to min_delay_seconds: 5.0 + jitter_seconds: 2.0 and recovery moved to the deferred retry pass.
- (2026-08-18) Symmetric request pacing is expressed via DelayPolicy.centred(center, jitter) (networking/rate_limiter.py), NOT by constructing DelayPolicy directly: wait() is additive (minimum + uniform(random_min, random_max)) and validate() forbids negative bounds, so "5 +/- 2" must be encoded as minimum=3 with a draw from [0, 4]. centred() raises ValueError when jitter > center. DEFAULT_JITTER_SECONDS = 2.0 is a module constant for the same slotted-dataclass reason as DEFAULT_MINIMUM_DELAY_SECONDS. The CLI also rejects --jitter-seconds > --min-delay-seconds with a BadParameter.
- (2026-08-20) Phase A and phase B share ONE RequestBudget that is never reset, and phase A runs to completion first. With max_pages=20 x 2 categories it wants 40 requests against a ~5-10 request burst, so it consumed the whole budget and phase B fetched nothing — that is why exports filled with card rows carrying no latitude/longitude. `deepen: true` (config/scrape.yaml, `--deepen/--no-deepen`) now seeds phase B from card-only rows already in the export and skips the search walk entirely. It falls back to the search walk on its own when no row is card-only, so a fresh checkout still works; `--no-deepen` is how you go discover new listings.
- (2026-08-20) Phase B flushes BEFORE the cooldown, not after: `request_permitted()` sleeps for the full ~25 minutes internally, so a post-cooldown flush left a whole burst of detail rows unsaved across the window where a run is most likely to be killed (which is how the 08-20 run lost its phase B). `RequestBudget.burst_is_spent` exists for this — it is the public read of the private `_burst_is_spent()`.
- (2026-08-20) parsers/search_card.py must resolve card hrefs against `_BASE_URL` before storing `canonical_url`. Cards can carry a root-relative href, and nothing consumed card URLs until the deepening path did, so exporting one verbatim only fails later with "URL must be an HTTPS Aruodas URL".
- (2026-08-18) pipelines/online.py runs ONE deferred retry pass (DEFAULT_RETRY_COOLDOWN_SECONDS = 300.0, public because the CLI uses it as an option default; retry_cooldown_seconds=0 disables). Listings that got BlockedError, plus listings never attempted because _MAX_CONSECUTIVE_BLOCKS abandoned the main pass, are queued as _DeferredListing and re-run through the shared _attempt_listing() helper after sleeper(cooldown). Recovered listings are removed from failed_urls.csv, so OnlineScrapeSummary.failed counts only post-retry failures; deferred_retries_attempted/_recovered report the pass. Blocked SEARCH pages are deliberately not retried (re-discovery would renumber pagination). process_online takes an injectable `sleeper` so tests never really wait; the _run helper in tests/integration/test_online_pipeline.py defaults retry_cooldown_seconds=0.0 so main-traversal tests assert exact request counts.
- (2026-08-21) The impersonation profile must AGREE with the browser that mints `cookie_file`, and this outranks any standalone judgement of a profile. PerimeterX binds a session to the identity that earned it, so a Chrome 151 cookie replayed over a chrome131 handshake contradicts itself on every request. Bumped chrome131 -> chrome146 (nearest available to the local Chrome 151). curl_cffi 0.16.0 ships chrome131, chrome133a, chrome136, chrome142, chrome145, chrome146 — the old "chrome136 is rejected, newer is not better" note was measured COOKIE-FREE, where there is no minting identity to agree with, and does not carry over to a cookied run. Step DOWN the list if 403s reappear, and re-check `chrome://version` before blaming the profile. NOT yet verified against the live origin: the run was mid-cooldown when this landed.
- (2026-08-21) The workstation constraints recorded in `docs/history/connectivity_fix_plan.md` (Playwright/Selenium impossible: Chrome `RemoteDebuggingAllowed: 0`, unsigned binaries refused with `WinError 1260`) are STALE — verified 2026-08-21. The Chrome and Edge policy keys are absent, user-mode code integrity is not enforced, Smart App Control is off, `pip.exe --version` runs, and `chrome.exe --remote-debugging-port` answers on CDP (Chrome/151.0.7922.173). Browser automation is therefore available again if the cookie path needs it. CLAUDE.md's "always invoke tools as modules, never via generated launchers" rule is likewise no longer forced by app control, though it remains harmless. Do not re-cite the old blocker without re-testing.
- (2026-08-21) A browser is NOT a parsing upgrade here: `docs/data_surface_assessment.md` establishes the site is classic server-rendered HTML with no `__NEXT_DATA__` or hydration payload. The only thing Playwright buys that curl_cffi cannot do is RUN the PerimeterX JS sensor to mint/refresh `_px3`. So the shape worth building, if this is revisited, is a cookie-minting service writing to the existing `cookie_file` seam — not a browser-based fetcher.
- (2026-08-20) Diagnosing "missing latitude/longitude" in data/processed/*.csv: ALWAYS check the `record_source` column first. Search-card rows (`record_source=search`, produced by parsers/search_card.py) physically cannot carry ~19 detail-only columns, because those values exist only on the listing detail page. The detail-only set is: municipality, neighbourhood, local_area, full_address, house_number, description_lt, listing_created_date, listing_updated_date, listing_age_days, views_count, saved_by_users_count, latitude, longitude, coordinate_source, coordinate_precision, building_type, energy_class, window_orientation, apartment_number, the garage/balcony/terrace/basement/storage/lift booleans, security_features, all_features_json, raw_attributes_json. A `search` row with empty lat/long is correct behaviour, NOT a parser bug in parsers/coordinates.py. Also note `_queue_from_existing_cards` in pipelines/online.py SHUFFLES the deepen queue (human-realism, same rationale as the phase-A visit order), so deepened rows are scattered randomly through the export rather than appearing in file order — patchy-looking coverage is expected.
- (2026-08-22) **A solved challenge is worth ~100+ requests; an unsolved one ~6.** Observed directly: a run died after 6 pages, the operator solved the px-captcha by hand in a browser, and the following run passed 100 requests without a refusal. The budget attaches to how the `_px3` cookie was EARNED, not to its freshness and not to the IP. `has_protection_token` is therefore a presence check, not a quality check — two cookies named `_px3` can differ by an order of magnitude in worth, and nothing in `BrowserCookie` can tell them apart. When a run dies at ~6 requests, re-mint through a solved challenge; do not wait, and do not start stepping impersonation profiles.
- (2026-08-22) **The old "sustained per-IP block" claim in docs/online_scraping.md was WRONG and has been retracted in place.** It asserted the origin serves px-captcha to every request from a spent address "including brand-new sessions with no cookies", and that no client-side change could lift it. Solving the challenge clears the state from the same address immediately. This mattered because the claim argued against the one fix that works and pointed at an allow-list request instead. The allow-list is still worth having — it removes the challenge step — but it is not the only remedy. Re-read the retraction before concluding "IP block" from a 403 again. Note this also narrows the (2026-08-18) count-not-rate finding: the ceiling is a request COUNT per cookie-trust-level, and pacing still buys nothing, but the count is not fixed per address.
- (2026-08-22) `mint-cookie` (cli.py -> networking/cookie_minter.py) replaces copying a Cookie header out of DevTools. Drives the installed Chrome via Playwright with `channel="chrome"`, HEADED, on a persistent profile at `<cookie dir>/browser_profile/`; polls `page.content()` for `px-captcha`, and on a clean page harvests cookies whose domain ends in `aruodas.lt` into a Cookie header written atomically by `cookie_source.write_cookie_file`. Headless is a test-only argument and must not be used operationally: headless Chrome puts `HeadlessChrome/151` in its own User-Agent and draws a challenge it cannot clear. The solve is intentionally NOT automated — it is the human attestation the raised budget pays for, and faking it falls outside the project's authorization. Playwright is an optional extra (`pip install -e .[browser]`), imported lazily in `_load_playwright()` so the package still installs and runs where no browser exists; CI never mints.
- (2026-08-22) `--solve-on-block` / `solve_on_block` lets a blocked run re-earn its session instead of waiting. `RequestBudget` takes an optional `renewer: Callable[[], bool]`; when a burst is spent it is tried FIRST, before the `max_empty_bursts` and `max_cooldowns` checks, because those bound how long a run may WAIT and a renewal costs no waiting — a run that can renew must not be stopped by a ceiling on waiting, including on the pass where waiting has already failed. Bounded separately by `BudgetPolicy.max_session_renewals` (DEFAULT_MAX_SESSION_RENEWALS = 10), which exists ONLY so a renewer that always returns True cannot spin forever; nothing else bounds it. Default `renewer=None` restores the exact wait-only behaviour, which is what CI and unattended runs get.
- (2026-08-22) `RequestBudget.session_renewed()` clears `_observed_ceiling`, `_burst_successes` and `_blocked` but deliberately NOT `_empty_bursts`. Clearing the ceiling is the whole point: it measured ONE cookie, and an unsolved-challenge session (~6 requests) versus a solved one (100+) differ by more than an order of magnitude, so carrying the old observation across would floor the new session at `minimum_burst` and send the run back into cooldowns the renewal just avoided. `_empty_bursts` is the guard against renewals that report success while the origin keeps refusing, so resetting it would disarm the one check that notices.
- (2026-08-22) `PageFetcher` gained `set_cookie`, implemented by both transports and delegated from `AruodasHttpClient.set_cookie`. Both implementations also clear the transport's own cookie jar, or the replaced session's accumulated cookies get merged with the new header and two generations of the same token go out on one request. Swapping on the LIVE client (rather than rebuilding it) is what lets a renewal keep the HTML cache and pacing state. Any test double for `PageFetcher` now needs `set_cookie` — `FakeFetcher` in tests/unit/test_transport.py records into `cookies_set`.
- (2026-08-22) `--solve-on-block` requires `cookie_file`: the renewed session has to be written somewhere and the browser profile that remembers solves lives at `<cookie dir>/browser_profile/`. The CLI exits 1 with that message rather than silently running without renewal. It also SUPPRESSES the stale-cookie startup refusal, since a run that can re-earn its session mid-flight no longer risks burning hours of cooldowns on a rotated cookie.
- (2026-08-22) CSV artifacts are written **utf-8-sig** (`constants.CSV_ENCODING`); JSON artifacts stay plain utf-8. Reported as "strange characters" in the export, but the bytes were always correct UTF-8 — Excel on Windows decodes a .csv with the legacy ANSI codepage unless it opens with a BOM, so `Visorių g.` displayed as `VisoriÅ³ g.`. The BOM removes Excel's guess. **Every CSV reader must use the same codec**: `export.read_records` parses the export back to merge by `listing_id`, and reading a BOM'd file as plain "utf-8" leaves the mark glued to the first header name, so `scrape_timestamp_utc` arrives unrecognised, every row looks new, and an additive run DUPLICATES instead of updating. `validation.records.validate_csv` has the same exposure. utf-8-sig is tolerant of a missing BOM, so pre-existing exports still load and no regeneration is needed. Do NOT put a BOM on the JSON artifacts — it is invalid to many parsers, `json.loads` included. Covered by tests/unit/test_csv_encoding.py.
- (2026-08-22) `max_pages` and `max_listings_per_category` bounds raised from 20/500 to `constants.MAX_SEARCH_PAGES = 500` and `constants.MAX_DETAIL_FETCHES_PER_CATEGORY = 20_000`, declared once and imported by BOTH run_config.py (pydantic `le=`) and cli.py (typer `max=`) — they were duplicated literals before, and a config rejected by pydantic never reaches typer, so raising one alone changes nothing. The old caps were guardrails against a typo, NOT limits the origin imposes: phase A follows the `next_page_url` the site itself serves, so pagination continues as long as Aruodas offers one. 20 pages x ~25 cards capped a category at ~500, which is exactly where a full Vilnius export stalled (498 apartments / 500 houses). Do NOT confuse the `max=20` on `max_cooldowns` in cli.py with these; it is unrelated and unchanged.
- (2026-08-22) Deep pagination is the weak half of a large traversal: search results re-sort between requests, so listings can be missed or double-counted the further in the walk goes. Partitioning a category into several narrower `search_url`s in cities.yaml (district, price band, room count) is more reliable than one very deep walk, and keeps each partition well inside the bounds. Note also that `deepen: true` skips phase A entirely when the export holds card-only rows, so `max_pages` is IGNORED in that mode — raising it while deepening changes nothing.
- (2026-08-22) `OnlineScrapeSummary.listings_new` counts listing_ids absent from the export BEFORE the run, computed against a `known_listing_ids` snapshot taken right after `_load_existing_records` and diffed against the merged result at the end. It is not `listings_discovered`, which counts cards seen this run INCLUDING ones already held — a second walk over the same pages re-sees nearly all of them, so `listings_discovered` measures effort while `listings_new` measures growth. Only `listings_new` falls to zero when the site has nothing new, which is the question a scheduled re-run actually asks. The CLI prints the "New this run" line only when `search_pages_fetched` is non-zero: a deepening run touches no search page and would otherwise always report zero new, reading as "the site had nothing".
- (2026-08-22) `export.append_run_history` writes `data/processed/run_history.csv`, one row per online run, append-only (`RUN_HISTORY_FIELDS`). `scrape_summary.json` is OVERWRITTEN every run so it can only describe the last one; the history is what survives to answer "how many publications do we know, and what did each walk add". Existing rows are read and rewritten rather than appended in place, to keep the repo-wide atomic-write invariant — one row per run keeps that cheap forever. Nothing in a row is recalculated from the export, so old rows stay true after later deepening. `tests/integration/test_online_pipeline.py` asserts the exact artifact set in the output directory, so adding an artifact there breaks it by design.
- (2026-08-22) `max_session_renewals` is now plumbed CLI -> run_config -> process_online -> BudgetPolicy (was hardcoded to the default 10). At ~100 requests per solved challenge, 10 capped an attended run at roughly 1000 requests, which silently stopped full-city walks about a tenth of the way in. config/scrape.yaml sets 200. It doubles as the honest bound on how many times the operator will be asked to solve a challenge.
- (2026-08-22) **A cache hit must not be charged against the request budget, nor counted as a page fetched.** Both phases previously bracketed `client.fetch` with `budget.request_permitted()` / `budget.record_success()` unconditionally, and `_attempt_listing` set `fetched=True` on any successful fetch — so a page read from disk consumed a burst slot, could trigger a ~25 minute cooldown, and inflated `search_pages_fetched` / `detail_pages_fetched`. This bit hardest on resume: pagination position is NOT persisted (`PaginationState` is per-run, in memory), so a restarted run replays every page it already holds from page 1, which under the old accounting spent the whole burst before reaching new ground. Fixed with `HtmlCache.has` -> `AruodasHttpClient.has_cached(url)`, checked BEFORE asking permission — checking after would already have bought the cooldown. `pages_served_from_cache` on the summary and in run_history.csv keeps the report honest, since `*_fetched` dropping is otherwise indistinguishable from the run doing less work. `refresh_cache=True` correctly bypasses the shortcut, because then the fetch really does hit the origin.
- (2026-08-22) Cache filenames are `sha256(url).hexdigest() + ".html"` (networking/cache.py) and nothing ever LISTS that directory — it is only ever asked "do you have this exact URL". What to fetch comes from two other places: search pages from `next_page_url`, parsed out of the HTML of the page just downloaded (discovery/listing_links.py, `/butai/vilniuje/puslapis/2/` shape — the category segment is pinned so a cross-category link cannot hijack the walk), and detail pages from `canonical_url` on rows where `record_source == "search"`. So the opaque names cost nothing functionally; the meaning lives in the CSV. `source_page_number` is a label on the record, never used to build a URL.
- (2026-08-22) The phase B to-do list is in memory only (`queued` list -> `pending` deque); there is no checkpoint file for it, and none is wanted. It is rebuilt from the export by `_queue_from_existing_cards`: a row with `record_source == "search"` is still owed a fetch. The CSV IS the durable queue, which is why a crash loses only ordering (already-shuffled anyway) and why the two states can never disagree.
- (2026-08-22) `ask_phase` (config + `--ask-phase`) prompts at the start of scrape-live for which phase to run, since deepening and discovery compete for one per-IP budget and a run does one or the other. Guarded three ways: skipped when `--deepen/--no-deepen` was passed on the COMMAND LINE (checked via `ParameterSource.COMMANDLINE`, same mechanism as `_resolve`), skipped when `sys.stdin.isatty()` is false so CI and unattended runs never block on a question, and skipped when nothing is card-only because then there is no choice. `_count_card_only` reads the export via `read_records` and swallows read errors deliberately — the run itself reports a bad export properly a moment later, and a prompt is the wrong place to fail. `online._selected_categories` was renamed to public `selected_categories` so the CLI can share it rather than duplicating the property_type mapping.
- (2026-08-22) The trap `ask_phase` exists to defuse: `deepen: true` skips phase A whenever ANY row is card-only, and rows are never deleted, so listings that can never be fetched (sold and removed, permanently 404) leave `queued` non-empty forever — every subsequent run would spend its requests re-trying corpses and never discover anything again. The prompt makes that visible. A code-level fix (falling through to phase A when the queue empties and budget remains, or giving up on a listing after N failed attempts) is still unimplemented.
- (2026-08-22) Dependencies have ONE source of truth: `pyproject.toml`. `requirements.txt` (which repeated `[project] dependencies` verbatim, same ten pins) and `requirements-dev.txt` were deleted; dev tooling moved to the `dev` extra. Install with `pip install -e ".[dev]"`; extras are `dev` and `browser` (playwright, for `mint-cookie` only). Both workflows were updated — ci.yml uses the extra, scrape-live.yml installs the package alone. Ruff stays out of the extra on purpose and is pip-installed by CI in its own step. Do not reintroduce a requirements file: nothing checked the two copies agreed.
